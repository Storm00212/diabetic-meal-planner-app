# How to build a service in this monorepo

Every backend service in GlucoPlate follows the same shape. If you can read
`apps/svc-auth`, you can read all of them.

```
apps/svc-<domain>/
├── prisma/
│   ├── schema.prisma      this service's database, and nothing else
│   └── seed.ts            idempotent seed for this service only
├── src/
│   ├── index.ts           entry point: load env, listen, shut down cleanly
│   ├── env.ts             loads .env before anything reads it  (import FIRST)
│   ├── app.ts             builds the Express app (no socket)
│   ├── config.ts          reads and validates the environment
│   ├── lib/
│   │   ├── logger.ts      structured logs: time, level, service, requestId
│   │   ├── prisma.ts      one PrismaClient per process
│   │   ├── errors.ts      ApiError + the error middleware shape
│   │   ├── jwt.ts         sign / verify access tokens
│   │   └── http.ts        asyncHandler, requestContext, requestLogger, requireAuth
│   └── modules/
│       └── <feature>/
│           ├── <feature>.routes.ts      HTTP: parse input, call the service
│           ├── <feature>.service.ts      business rules, no HTTP, no SQL
│           └── <feature>.repository.ts   database access, owner-scoped
└── package.json
```

## The rules

1. **One database per service.** A service never reads another service's
   tables. `userId` is a plain integer copied from the caller's token, not a
   foreign key.

2. **`prisma/` is private.** Another service cannot see these models. If you
   need data from another service, call its HTTP API.

3. **Every route lives in a module.** No route handlers in `app.ts`.

4. **Ownership is enforced in the query.** `where: { id, userId }`, not in the
   UI.

5. **One error shape.** Throw `ApiError`; the error middleware turns it into
   `{ error, code, requestId }`.

6. **Every request is traced.** `requestContext` assigns an `x-request-id`,
   `requestLogger` logs it, and the response echoes it back.

## Environment variables

Each service has its own `.env` (git-ignored, generated by `npm run env:sync`).

| Variable | Meaning |
|---|---|
| `PORT` | The explicit local port. See `SERVICE_PORTS` in `@glucoplate/types`. |
| `DATABASE_URL` | Pooled connection. **Must include `?pgbouncer=true`** — the pooler is in transaction mode and Prisma cannot use prepared statements through it. |
| `DIRECT_DATABASE_URL` | Direct connection, used by `prisma db push` and seeds. No `pgbouncer=true`. |
| `JWT_SECRET` | Shared with every other service, so a token minted by svc-auth is accepted everywhere. |
| `CORS_ORIGINS` | Comma-separated list, or `*`. |
| `LOG_LEVEL` | `debug \| info \| warn \| error \| silent`. |
| `SVC_*_URL` | Where the other services live, for service-to-service calls. |

## Adding a service

```bash
mkdir -p apps/svc-<name>/{src/lib,src/modules/<name>,prisma}
```

Then copy `apps/svc-auth` and adjust:

1. `package.json` — name `@glucoplate/svc-<name>`, port in `scripts`.
2. `prisma/schema.prisma` — only this service's tables.
3. `src/config.ts` — service name and port.
4. `src/modules/<name>/` — the feature module.
5. `turbo.json` — no change; the pipeline is generic.
6. `packages/types/src/index.ts` — add the service to `SERVICE_PORTS` and
   `SERVICE_NAMES`.
7. `scripts/sync-env.mjs` — add the service to `SERVICE_PORTS` and
   `DB_PORTS`.
8. `apps/gateway/src/routes.ts` — route the service's paths.

## Service-to-service calls

Forward the caller's `Authorization` header. Every service verifies the same
JWT, so the downstream service knows exactly who is asking.

```ts
const response = await fetch(`${catalogUrl}/api/dishes`, {
  headers: { Authorization: req.header("authorization") ?? "" },
});
```

Cache the result for a short TTL so a cold downstream service is not hit on
every request — and so a sleeping service cannot make the caller wait.

## Health check

Every service exposes `GET /api/health`:

```json
{ "ok": true, "service": "svc-auth", "database": "connected" }
```

It returns 503 when the database is unreachable, so a load balancer or the
gateway can tell the difference between "up" and "up but broken".
